# Artificial Intelligence User Guide

This document explains the AI features of the program **without requiring technical
knowledge**: what the AI does, what it does not do, what the difference between the
green and purple panels on screen is, and how much you should trust an AI
interpretation.

> Version: 0.9.0 · Interface: the **AI Center** screen (requires the `ai:use` permission)

---

## 1. What the AI Does in This Program

The AI in this program **does not produce numbers; it translates computed numbers
into human language.** The flow is:

```
1. The program computes real numbers from the database   → REAL DATA
2. That computed summary is sent to the AI
3. The AI interprets it and writes possible causes and recommendations → AI INTERPRETATION
4. The screen shows the two in SEPARATE panels
```

The AI is never given raw database access. It always receives a **pre-computed,
verifiable summary** together with the instruction "answer based on the real data
above, do not alter the numbers".

### What the AI concretely does

| What it does | Example |
|---|---|
| Turns numbers into sentences | Takes "attendance rate 78%" and says "attendance is 7 points below target, with the drop concentrated in the Saturday morning group" |
| Lists possible causes | For rising absence it produces hypotheses such as "school exam period", "transport", "lesson time" |
| Writes recommendations | "Try moving the Saturday 09:00 group to 10:30" |
| Drafts a training plan | Sees the athlete's weakest stroke and improvement trend and drafts a 4-week plan |
| Writes a management summary | Pulls the weekly operations and finance summary into report language |
| Chats | You can ask free-form questions on the AI Center → Chat tab |

### What the AI does NOT do

* **It does not calculate.** Attendance rate, occupancy, revenue, improvement
  percentage, readiness score — the program computes all of them. These numbers work
  exactly the same with the AI switched off.
* **It does not change data.** It creates no student record, deletes no lesson,
  enters no payment.
* **It does not decide.** Approval, execution and responsibility remain yours.
* **It does not know the future.** A race result, next month's revenue, whether a
  student will leave — those are interpretations at best, not predictions.

## 2. The REAL DATA / AI INTERPRETATION Split

This is the most important design decision in the program. An analysis result is
always shown in **two separate panels**.

### 2.1 The green panel — Real Data

```
┌─────────────────────────────────────────────────┐
│ ✓  REAL DATA                                    │  ← green frame, check mark
│    This section is computed from the database   │
│                                                 │
│  • Ayşe Yılmaz · 24 performance records         │
│  • 50 m freestyle: best 33.10, first→last       │
│    35.20→33.40 (-1.80 s, -5.11%), trend:        │
│    improving                                    │
│                                                 │
│  [ Active students: 412 ] [ Attendance: 78.4% ] │
└─────────────────────────────────────────────────┘
```

* **Source:** the Statistics Engine (`statistics_engine.py`) — straight from the
  database.
* **Accuracy:** exact. The same data always yields the same result, verified by 395
  tests.
* **How to use it:** **base your decisions on this panel.** The number you take into
  a report, a parent meeting or a staff review comes from here.

### 2.2 The purple panel — AI Interpretation

```
┌─────────────────────────────────────────────────┐
│ ✦  AI INTERPRETATION      [ local · llama-3.3 ] │  ← purple frame, ✦ mark
│                                                 │
│  The athlete shows steady acceleration in the   │
│  50 m freestyle over the last three months...   │
│                                                 │
│  Possible Causes                                │
│   • Increased training volume                   │
│   • A technical correction settling in          │
│                                                 │
│  Recommendations                                │
│   • Consider more turn work                     │
│                                                 │
│  ⓘ This interpretation was generated by an AI   │
│    model and is not established fact. Base your │
│    decisions on the computed metrics above.     │
└─────────────────────────────────────────────────┘
```

* **Source:** a language model (local LM Studio or cloud NVIDIA).
* **Accuracy:** variable. Ask the same question twice and the wording may differ. The
  warning text at the bottom of the panel is always visible.
* **Badge:** the top-right of the panel states which provider and which model
  produced the text.

### 2.3 Why the split exists

1. **Accountability.** If you tell a parent "your child's attendance is 62%", that
   number must be exact. The chance of an AI rounding or mixing up a number while
   forming a sentence is not zero — which is why a number is never read from the AI
   panel alone.
2. **Working without AI.** If the local model is off, there is no internet, or no API
   key is configured, the green panel **still works**. The system does not depend on
   AI.
3. **Auditability.** Because the panels are separate, you can check line by line which
   data an interpretation rests on.
4. **Legal and ethical ground.** Decisions made about students and parents must have a
   traceable, explainable basis.

### 2.4 How to approach an AI interpretation

| Approach | Correct? |
|---|---|
| "The AI said so, we are doing it" | ✗ Wrong |
| "The AI listed three causes; two made sense to us and we checked them against the data" | ✓ Correct |
| Copying a number out of an AI sentence into a report | ✗ Wrong — take the number from the green panel |
| Opening an AI recommendation for discussion in an instructor meeting | ✓ Correct |
| Presenting an AI interpretation to a parent as "what the system says" | ✗ Wrong |
| Using the AI as a first look / idea generator | ✓ Correct |

**Golden rule:** an AI interpretation is a **colleague's opinion**, not a measurement.
You would ask a colleague "why do you think that?" too.

## 3. The AI Center Screen

Open **AI Center** from the left menu. The screen has six tabs:

| Tab | What it is for |
|---|---|
| **Control Center** | Provider status, latency, model list, token usage |
| **Analysis** | Running data analyses (the tab you will actually use) |
| **Chat** | Free-form question and answer |
| **Routing** | Which model is recommended for which kind of task |
| **Task History** | Past AI calls: provider, model, tokens, duration, outcome |
| **Settings** | Provider configuration (visible only with `ai:configure`) |

### 3.1 Provider status

The Control Center shows a card per provider:

| Field | Meaning |
|---|---|
| **Enabled** | Whether it is switched on in settings |
| **Available** | Whether it is actually responding right now |
| **Endpoint** | The server address in use (e.g. `http://localhost:1234/v1`) |
| **Model** | The model name being used |
| **API key** | Whether one is configured — **always shown masked** (`nvi************a1b2`) |
| **Latency** | The server's response time in milliseconds |
| **Model count** | How many models are reachable at the provider |
| **Last checked** | When the status was last measured |
| **Error message** | Why it is unreachable, if it is |
| **Privacy note** | For local, "data never leaves your computer"; for cloud, "data is processed on NVIDIA servers" |

The card colour summarises the state: a reachable provider is green, a disabled one
grey, a failing one red.

### 3.2 How to read latency

Latency is the response time of the provider's **health check**; it is not how long an
analysis takes.

| Latency | Interpretation |
|---|---|
| < 200 ms | Very good (typically a local model) |
| 200–800 ms | Normal |
| 800–3000 ms | Slow; possibly network latency at a cloud provider |
| No response / timeout | LM Studio is closed, no model is loaded, or there is no internet |

The real analysis duration appears in the purple panel and in the **Task History** tab
as `duration_ms`. On a local model a long analysis can take 20–60 seconds; that is
normal (the default timeout is 180 seconds).

### 3.3 Token usage

A **token** is the unit a model counts while processing text; roughly 4 characters ≈
1 token. The Control Center shows two counters:

* **Today** — total tokens today (prompt + response)
* **Total** — all time

Why it matters: at a cloud provider, token consumption means **cost and quota**. On a
local model there is no charge, but a high token count means slower answers.

A **24-hour error counter** and **task-type counters** are shown as well. If the error
counter keeps climbing, something is wrong in the provider configuration.

### 3.4 Connection test

You can run a **6-stage test** for each provider. Each stage reports
`PASS` / `FAIL` / `SKIPPED`:

| # | Test | What it tries |
|---|---|---|
| 1 | `connection` | Is the server reachable, how many models are listed |
| 2 | `model` | Can the model list be fetched |
| 3 | `simple_prompt` | Does a simple question get an answer |
| 4 | `json_output` | Can the model return output in the requested JSON shape |
| 5 | `timeout` | Does the answer arrive within the timeout limit |
| 6 | `streaming` | Does streaming (word-by-word output) work |

If the provider is disabled or has no API key, all six return `SKIPPED`. If the
connection cannot be established, test 1 is `FAIL` and the remaining five are
`SKIPPED`.

## 4. Running an Analysis

**AI Center → Analysis** tab.

### 4.1 Step by step

1. **Choose the analysis topic (scope).** This decides which data the program will
   compute and send to the AI.
2. **Type your question** or click one of the ready-made questions.
3. If the topic concerns a student (a `Student required` badge appears), **select the
   student**.
4. Optionally choose a **date range** and a **provider** (automatic / local / cloud).
5. Press **Analyse**.
6. The green panel appears first, then the purple one.

### 4.2 Analysis topics

| Topic | What it computes |
|---|---|
| General overview | All dashboard counters |
| Student performance | The selected athlete's times and improvement across all events |
| Training suggestion | The same performance data, from a coaching angle |
| Weakest stroke | The same performance data, focused on stroke comparison |
| Declining students | Athlete-event pairs that regressed over the last 90 days |
| Top improvers | Athlete-event pairs that got fastest over the last 90 days |
| Competition readiness | The statistical readiness scores of the last 60 days |
| Attendance | The period's present, absent, late and excused rates |
| Retention | Registrations/departures, retention, churn and cohort data |
| Finance | Period income, expenses, net, outstanding receivables, overdue invoices |
| Instructor workload | Lessons, hours, occupancy, attendance and cancellations per instructor |
| Schedule optimisation | Pool occupancy, hourly/daily load, free capacity |
| Free lanes | The same pool data, focused on empty hours |
| Payment risk | Overdue invoices and memberships expiring within 14 days |

### 4.3 Ready-made questions

At the bottom of the screen there is a library of **18 ready-made questions** (5 are
developer-oriented and appear only in the AI Developer Console). Clicking one fills
the question box and selects the correct analysis topic automatically.

The 13 ready-to-use questions: analyse student performance, find students with
declining performance, create a 4-week training plan, identify the weakest stroke,
top improvers, athletes ready for competition, optimise the lesson schedule, find
free lanes, balance instructor workload, payment risk, why student churn increased,
this week's management report, and analyse attendance rates.

### 4.4 Reading the result

| Section | Where it comes from | How to read it |
|---|---|---|
| Green panel — bullet list | Computed summary | The basis for your decision |
| Green panel — cards and tables | Detailed metrics | Take your numbers from here |
| Purple panel — interpretation | AI | An opinion; verify it |
| Purple panel — Possible Causes | AI | At most 8 items; hypotheses, not evidence |
| Purple panel — Recommendations | AI | At most 8 items; evaluate before acting |
| Purple panel — badge | System | Which provider and model were used |
| Bottom warning | System | Always visible, cannot be dismissed |

**The "insufficient data" notice:** if the number of computed data points is **below
3**, the AI is not called at all. The green panel still appears and an informational
message replaces the purple panel. This is a deliberate safeguard: inferring a "trend"
from 2 records is misleading.

## 5. Example Questions and How to Interpret Them

### Example 1 — A single athlete's performance

> **"Analyse Ahmet's 50 m freestyle performance over the last 3 months"**
> Topic: *Student performance* · Student: Ahmet Kaya · Range: last 3 months

**What you will see in the green panel:** record count, best/mean/median time,
standard deviation, first→last time, improvement in seconds and percent, 30- and
90-day change, trend label (`improving` / `declining` / `stable`).

**How to interpret it:** look first at the **trend label** and the **improvement
percentage**. In swimming a smaller time is better, so a negative second difference is
good news. Verify the AI's phrase "clear improvement" against the `-5.11%` in the
green panel. If the record count is below 5, both the trend and the interpretation are
weak.

---

### Example 2 — Athletes with declining performance

> **"Find students whose performance is declining and assess possible causes"**
> Topic: *Declining students*

**Green panel:** athlete-event pairs that regressed over the last 90 days; each row
shows baseline mean, recent mean, decline in seconds and percent, record count and
last record date.

**How to interpret it:** entering the list requires at least 4 records and at least a
1% decline. The 1–2% band can be ordinary fluctuation; **above 4% is a real signal.**
The causes the AI lists (fatigue, technical breakdown, motivation) are **hypotheses** —
do not decide without talking to the athlete and the instructor. Check the same
athlete's attendance record as well.

---

### Example 3 — Competition readiness

> **"Which athletes appear more prepared for the competition? Explain with reasons"**
> Topic: *Competition readiness*

**Green panel:** a readiness score (0–100) per athlete-event, best time, recent mean,
consistency (standard deviation), trend and record count for the period.

**How to interpret it:** the score is **statistical, not an AI prediction**:
consistency 25% + form 35% + trend 25% + volume 15%. It knows nothing about
competitors, course type or daily form. Its correct use is **ranking athletes against
each other within the same event**. The answer to "who will win" is not here.

---

### Example 4 — Attendance rates

> **"Analyse attendance rates and suggest ways to reduce absence"**
> Topic: *Attendance*

**Green panel:** overall attendance rate, present/absent/late/excused counts, no-show
rate, breakdown by group and instructor, lowest-attendance students.

**How to interpret it:** late arrivals and make-up attendees count as **present**;
excused absence **lowers** the rate. If the AI says "attendance dropped", add the
seasonal effect yourself — exam periods and the illness season lower this rate
structurally. In the group breakdown, groups with few records have volatile rates.

---

### Example 5 — Student churn

> **"Why did our student churn increase in the last three months? Explain from data"**
> Topic: *Retention*

**Green panel:** active students, new registrations, departures, retention %, churn %,
average membership days, comparison with the previous period, and the cohort table for
the last 6 months.

**How to interpret it:** the most valuable piece is the **cohort table**: it shows
which registration month erodes in which month. Causes the AI proposes such as "a
price increase" have no data behind them in the system — match them against events you
actually know about. If a cohort has 5–10 members, a single departure shows as a
10–20% drop.

---

### Example 6 — The lesson schedule

> **"Review the current lesson schedule and suggest occupancy improvements"**
> Topic: *Schedule optimisation*

**Green panel:** overall pool occupancy, busiest and quietest hour, most used lane,
unused capacity in hours, hourly and daily load distributions.

**How to interpret it:** the occupancy denominator covers every open hour and **every
day**; 100% is impossible. Do not panic when the AI says "occupancy is low" — use your
own facility's realistic band (usually 45–55%) as the reference. Before acting on a
time-shift suggestion, check **instructor availability and the pool maintenance
calendar** — neither is in the summary sent to the AI.

---

### Example 7 — Instructor workload

> **"Review instructor workloads and suggest rebalancing"**
> Topic: *Instructor workload*

**Green panel:** lesson count, total hours, occupancy %, attendance %, cancellation %,
and the private/group split per instructor.

**How to interpret it:** this table is **not a performance appraisal**. Occupancy is
set by the schedule, attendance by the students. If the AI says "instructor X is
inefficient", do not accept it — low occupancy is most likely a badly chosen lesson
slot. The ratios of an instructor with 3 lessons in the period are statistically
meaningless.

---

### Example 8 — Payment risk

> **"Identify memberships with payment risk and suggest a collection strategy"**
> Topic: *Payment risk*

**Green panel:** the number and total value of overdue invoices, details of up to 40
invoices (student, balance, days overdue, due date), and the number of memberships
expiring within 14 days.

**How to interpret it:** the numbers are exact; use the AI for **tone and
prioritisation**. Never send a message to a parent verbatim from AI text — payment is
a sensitive matter, and your institutional voice and data-protection obligations are
yours to define.

---

### Example 9 — Management summary

> **"Write this week's operations and performance summary for management"**
> Topic: *General overview*

**Green panel:** active students, today's lessons, pool occupancy, monthly
income/expense, overdue payments, expiring memberships, upcoming competitions, number
of declining athletes.

**How to interpret it:** the summary the AI writes is a good **draft**. Before it goes
to a board, verify every number against the green panel and attach the **Reports →
Weekly Management Report** (PDF/Excel) as the formal document.

---

### Example 10 — Weakest stroke

> **"Identify this athlete's weakest stroke and suggest improvements"**
> Topic: *Weakest stroke* · Student selection required

**Green panel:** mean improvement percentage per stroke, plus the strongest and
weakest stroke labels.

**How to interpret it:** the "weakest stroke" is **the one that improved least** — not
necessarily the slowest one in absolute terms. If the athlete rarely swims butterfly,
that stroke may look weak simply because of too few records. Always check the record
count per event.

## 6. The Training Plan Suggestion

**Performance → Student → AI Training Plan**, or the *Training suggestion* topic in
the AI Center.

The program computes the athlete's performance summary, sends it to the AI and creates
a plan record from the response.

### 6.1 The plan is a DRAFT

The generated plan is written to the database with **`is_approved = false`** and the
response carries `requires_approval: true`. That means:

* The plan **is not in force**. It is assigned to nobody as a lesson programme.
* **It is not applied until an instructor approves it.**
* The record carries `ai_generated = true` plus the provider and model used — so it is
  always traceable who produced what.
* The response ends with a warning text that cannot be dismissed.

### 6.2 What the instructor must do

1. Open the plan and check the **focus area** (filled automatically from the athlete's
   weakest stroke).
2. Check the athlete's **age, level and medical note** — these are **not** in the
   summary sent to the AI. This step is mandatory for baby and toddler groups.
3. Match the weekly lesson count, pool availability and competition calendar to the
   plan.
4. Make the necessary adjustments.
5. Approve it. An unapproved plan is applied nowhere.

> **Health warning:** the AI does not know the athlete's injury history, chronic
> conditions or medical restrictions. For adaptive swimming and for athletes with a
> medical note, do **not even treat the AI plan as a starting point**; prepare it
> together with the relevant instructor and medical staff.

## 7. Local AI vs Cloud AI

The program supports three provider kinds: **LM Studio (local)**, **NVIDIA Build
(cloud)** and generic **OpenAI-compatible** servers.

| | Local (LM Studio) | Cloud (NVIDIA Build) |
|---|---|---|
| **Where the data goes** | Nowhere — it stays on your computer | It is sent to NVIDIA servers |
| **Internet required** | No | Yes |
| **Cost** | None | Depends on the provider's quota/tariff |
| **Speed** | Depends on your machine; very fast on a strong one | Generally fast, network-dependent |
| **Model quality** | Depends on the model you downloaded | Large models are available |
| **Setup** | You must install LM Studio and download a model | Just an API key |
| **Outages** | Works whenever the program is open | Affected by provider outages |

The privacy notes in the Control Center repeat this on every card:

* Local: *"Local model: data never leaves your computer. Recommended for sensitive
  student data."*
* Cloud: *"Cloud model: submitted data is processed on NVIDIA servers. Be careful when
  sending personal data."*

### 7.1 Which one, when

| Situation | Recommendation |
|---|---|
| An analysis containing student names, medical notes or guardian information | **Local** |
| Any analysis about minors | **Local** |
| A management summary containing only totals and ratios (no names) | Cloud is acceptable |
| No internet | Local (the only option) |
| The local machine is weak and analysis is very slow | Cloud — but first check whether names are involved |
| Your institutional privacy policy forbids data leaving the premises | **Local only**; disable the cloud provider in settings |

### 7.2 Automatic fallback

The default mode is **automatic**. The system tries providers in the order defined in
the `.env` chain (default: `local,nvidia`). If the first does not respond, it moves to
the second. The badge on the purple panel tells you which one answered.

If you want to stay local-only, set the mode to **local**; no data then leaves the
computer.

## 8. When the AI Is Not Working

**The rest of the system keeps working normally.** This is the architecture's core
guarantee: AI is an add-on, not a dependency.

Everything that **keeps working** with AI switched off:

* Student, guardian, instructor, lesson, attendance, membership and finance records
* Calendar, conflict detection, lane planning
* **All statistics** — attendance rate, occupancy, retention, improvement percentage
* **The competition readiness score** (it is statistical, not AI)
* **All 16 report types and PDF/Excel/CSV export**
* The KPI dashboard, notifications, backups

The only thing you lose is **the interpretation text in the purple panel**.

### 8.1 Symptoms and fixes

| Symptom | Likely cause | What to do |
|---|---|---|
| An "AI unavailable" notice instead of the purple panel | The provider is not responding | Check the provider card in the Control Center |
| An "insufficient data" message | Fewer than 3 computed data points | Choose a wider date range or enter more records |
| The local provider is red | LM Studio is closed or no model is loaded | Open LM Studio, load a model, start the server |
| The cloud provider is red | Missing/invalid API key, or no internet | Define the key as `NVIDIA_API_KEY` in `.env`; without a key the cloud provider is **not considered enabled** |
| Analysis is very slow | The local model is large and the machine is struggling | Try a smaller model or switch to the cloud provider |
| Timeout error | The model could not answer within 180 seconds | Increase the timeout in settings or use a smaller model |
| The AI Center screen is not visible at all | You lack the `ai:use` permission | Ask your administrator |
| The Settings tab is missing | You lack `ai:configure` | Only administrators hold this permission |

### 8.2 An AI failure never causes data loss

When an AI call fails, the program does not raise an error; it simply returns the green
panel and flags `ai_available: false`. The failed call is written to the **Task
History** tab with its error message, so you can investigate it afterwards.

## 9. Limitations and Things to Watch

### 9.1 When the AI gets it wrong

| Situation | Why it errs | What to do |
|---|---|---|
| **Too little data** | A "trend" drawn from 3–5 records is noise | Look at the record count in the green panel; if it is low, do not take the interpretation seriously |
| **Seasonality** | The summary sent to the AI carries no seasonal context; it may read a summer dip as a "crisis" | Compare with the same period last year yourself |
| **Missing context** | Pool renovation, an instructor change, a price increase, the school exam calendar — none of these are in the data | Add the events you know about yourself |
| **A tendency to assert causes** | Language models are inclined to build "because" sentences and can present correlation as causation | Treat every "because" sentence with suspicion |
| **Invented numbers** | Rarely, a model can produce a number that is not in the summary | Look for every number of the interpretation in the green panel; if it is not there, do not trust it |
| **Overconfident language** | The model may use words like "certainly" or "clearly" | Such phrasing is not evidence |
| **Model differences** | A small local model and a large cloud model differ in interpretation quality | The badge tells you which model was used |

### 9.2 Things you must never do

* Present an AI interpretation as **a formal assessment** to a parent, a student or a
  staff member.
* Make AI output the **sole basis** for decisions such as performance appraisal,
  dismissal or non-renewal of a contract.
* Apply an AI-suggested training plan **without instructor approval**.
* Rely on an AI interpretation in health, injury or medical matters — that area is the
  responsibility of **medical staff**.
* Send a personal assessment about a child to a cloud provider.

### 9.3 Always remember

> The warning at the bottom of the purple panel cannot be dismissed and appears with
> every response:
>
> *"This interpretation was generated by an AI model and is not established fact. Base
> your decisions on the computed metrics above."*
>
> That sentence is not a formality; it is a rule of use.

## 10. Privacy — Which Data Goes Where

### 10.1 What is sent to the AI during an analysis

The package sent consists of three parts:

1. **Your question** (the text you typed)
2. **The computed summary** — for example "Ayşe Yılmaz · 24 performance records ·
   50 m freestyle: best 33.10..."
3. **Detailed metrics (JSON)** — capped at 6000 characters

If the scope is student-based, the **athlete's full name** is sent as well.

### 10.2 What is NEVER sent to the AI

| Not sent | Reason |
|---|---|
| National ID number, address, e-mail | They do not appear in the metric summary |
| Guardian contact details | Not in the summary |
| Passwords and password hashes | They never leave any layer of the system |
| API keys | They are masked even in the interface |
| Medical notes and special-needs information | Protected by `student:read_sensitive`; not part of the metric summary |
| Raw database tables | The AI only receives the computed summary |
| Payment card details | Not stored by the system |

### 10.3 The route the data takes

| Provider | Route | Who can see it |
|---|---|---|
| **Local (LM Studio)** | Program → `http://localhost:1234` → the model on the same computer | Only you. The data never leaves the network interface |
| **Cloud (NVIDIA Build)** | Program → HTTPS → `integrate.api.nvidia.com` | NVIDIA's terms of service apply |
| **OpenAI-compatible** | Program → the address you configured | Depends on who operates that address |

### 10.4 Records and logging

* Every AI call is written to **Task History**: provider, model, token count,
  duration, success/failure. That record lives in your local database.
* **Prompt texts are not logged by default.** The `AI_LOG_PROMPTS` setting is off by
  default and is meant only for debugging.
* API keys are written to no log line and appear masked in the interface.

### 10.5 GDPR / data-protection practice

1. **Run analyses containing personal data through the local provider.** This is the
   simplest and safest rule.
2. If you will use a cloud provider, make sure your organisation's privacy notice
   covers **international data transfer**.
3. Avoid cloud providers for analyses about minors.
4. To switch cloud usage off entirely: **AI Center → Settings** → disable the NVIDIA
   provider and set the mode to **local**. No data then leaves the computer.
